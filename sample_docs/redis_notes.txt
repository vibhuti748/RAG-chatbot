Redis is an in-memory data store that is often used as a cache in front of a slower database. Because the data lives in memory rather than on disk, reads and writes usually complete in well under a millisecond. A common pattern is called cache-aside. The application first asks Redis for the value it needs. If the value is there, that is called a cache hit and the database is never touched. If the value is missing, that is a cache miss, so the application reads the value from the database, stores a copy in Redis with an expiry time, and returns it to the caller. The next request for the same value is then served from memory.

Setting an expiry time, also known as a time to live or TTL, is important. Cached data can become stale when the underlying record changes, and an expiry guarantees that old values eventually disappear on their own. Short expiry times keep data fresh but reduce the hit rate, while long expiry times improve speed but risk serving outdated answers. Teams pick the value based on how often the data changes and how harmful a stale answer would be.

Redis is also commonly used for rate limiting. A simple fixed window limiter increments a counter for each client, such as an IP address, every time a request arrives. The first increment also sets an expiry equal to the window length, for example sixty seconds. When the counter passes the allowed limit, the service rejects further requests with the HTTP status 429, which means too many requests, until the counter expires and resets. This protects an API from abuse and accidental overload.

Beyond caching and rate limiting, Redis supports lists, sets, sorted sets and streams. These make it useful for job queues, leaderboards, session storage and lightweight messaging between services. For data that must never be lost, a traditional database remains the source of truth, and Redis is treated as a fast helper that can be rebuilt if it is ever cleared.
